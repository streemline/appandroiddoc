## Документація для розробників "Time Tracking System"

**Версія:** 1.0
**Дата:** 14 квітня 2025

Цей документ надає технічну інформацію, необхідну розробникам для розуміння архітектури, структури коду, ключових компонентів та принципів розробки мобільного застосунку "Time Tracking System" для Android.

**1. Загальна архітектура**

Застосунок розроблено з використанням архітектурного патерну **MVVM (Model-View-ViewModel)**, що сприяє розділенню відповідальності між UI-елементами, логікою представлення та даними.

* **Model:** Шар даних, що відповідає за зберігання та отримання даних. У цьому проєкті представлений Entity-класами (наприклад, `User`, `TimeEntry`) та локальною базою даних (SQLite через Room Persistence Library).
* **View:** Шар представлення, що відображає дані користувачеві та обробляє його дії. Представлений Activity, Fragments та Layout-файлами.
* **ViewModel:** Шар логіки представлення, що надає дані для View та обробляє дії користувача, не маючи прямого посилання на View. ViewModel отримує дані з Repository та надає їх у форматі `LiveData` для спостереження View.

**3. Ключові компоненти та їх призначення**

* **Data Layer (`com.example.timetracker.data`)**:
    * **`local`**: Відповідає за роботу з локальною базою даних SQLite через Room.
        * **`dao`**: Містить інтерфейси DAO (`TimeEntryDao`, `UserDao`) для виконання CRUD-операцій з таблицями `time_entries` та `users`. Використовує анотації Room (`@Query`, `@Insert`, `@Update`, `@Delete`).
        * **`db`**: Містить клас `AppDatabase`, який є абстрактним класом, що розширює `RoomDatabase` та надає доступ до DAO-інтерфейсів. Єдиний екземпляр бази даних створюється за допомогою Singleton-патерну.
        * **`model`**: Містить Entity-класи (`TimeEntry`, `User`, `MonthlyReport`), які представляють таблиці бази даних. Анотовані `@Entity` для визначення їх як таблиць Room.
    * **`repository`**: Містить класи репозиторіїв (`TimeEntryRepository`, `UserRepository`), які виступають посередниками між ViewModel та джерелами даних (локальна база даних, а в майбутньому - мережа). Репозиторії інкапсулюють логіку отримання та маніпулювання даними. Використовують DAO для взаємодії з базою даних та класи експорту (`ExcelExporter`, `PdfExporter`, `CSVExporter`).

* **UI Layer (`com.example.timetracker.ui`)**:
    * **`components`**: Містить кастомні UI-компоненти, які використовуються у фрагментах для відображення анімацій та специфічних елементів інтерфейсу (`AnimatedVisibilityComponent`, `AnimatedListComponent`, `FadeOutAnimationComponent`, `MonthCardComponent`).
    * **`input`**: Містить фрагмент `InputTimeEntryFragment` для додавання та редагування записів робочого часу.
    * **`main`**: Містить основну активність `MainActivity`, яка відповідає за навігацію між фрагментами.
    * **`profile`**: Містить фрагмент `ProfileFragment` для відображення та редагування профілю користувача.
    * **`statistics`**: Містить фрагмент `StatisticsFragment` для відображення статистики робочого часу та адаптер `TimeEntryAdapter` для відображення списку записів у `RecyclerView`.

* **ViewModel Layer (`com.example.timetracker.viewmodel`)**:
    * Містить класи `ViewModel` (`TimeEntryViewModel`, `UserViewModel`), які готують та надають дані для UI-елементів у форматі `LiveData`. ViewModel не містять логіки UI та переживають зміни конфігурації Activity/Fragment. Вони отримують дані з репозиторіїв та надають їх для спостереження View.

* **Utils Layer (`com.example.timetracker.utils`)**:
    * Містить утилітарні класи, такі як `DateUtils` для роботи з датами та часом, а також класи для експорту даних у різні формати (`ExcelExporter`, `PdfExporter`, `CSVExporter`).

**4. Основні технології та бібліотеки**

* **Kotlin:** Основна мова розробки застосунку (або Java).
* **Android Jetpack:** Набір бібліотек від Google для спрощення розробки Android-застосунків:
    * **ViewModel:** Для керування даними, пов'язаними з UI, з урахуванням життєвого циклу компонентів.
    * **LiveData:** Observable-клас даних, який є життєво-чутливим.
    * **Room Persistence Library:** Абстракція над SQLite для зручної роботи з локальною базою даних.
    * **Data Binding / View Binding:** Для спрощення взаємодії між макетами XML та кодом.
    * **Navigation Component:** Для керування навігацією між фрагментами.
    * **Coroutines:** Для спрощення виконання асинхронних операцій.
* **Бібліотеки для експорту:**
    * **iTextPDF:** Для створення PDF-документів.
    * **Apache POI:** Для роботи з файлами Excel (формат XLSX).
    * Вбудовані засоби Kotlin/Java для роботи з CSV.
* **Gradle:** Система збірки проєкту.
* **JUnit, Mockito/MockK, Espresso:** Фреймворки для юніт-, інтеграційного та UI-тестування.

**5. Принципи розробки**

* **Розділення відповідальності (SoC):** Кожен компонент (Activity, Fragment, ViewModel, Repository, DAO, Entity) має чітко визначену відповідальність.
* **Принцип єдиної відповідальності (SRP):** Кожен клас повинен мати лише одну причину для зміни.
* **Використання LiveData:** Для забезпечення життєво-чутливого спостереження за даними між ViewModel та View.
* **Асинхронність:** Виконання тривалих операцій (наприклад, операції з базою даних, експорт файлів) в окремих потоках або за допомогою Coroutines, щоб не блокувати основний потік UI.
* **Обробка помилок:** Реалізація механізмів обробки помилок та виняткових ситуацій.
* **Тестування:** Написання юніт-, інтеграційних та UI-тестів для забезпечення якості та стабільності коду.
* **Коментування коду:** Докладне коментування коду для покращення його розуміння та підтримки.
* **Дотримання стандартів кодування Kotlin (або Java).**

**6. Інструкції з внесення змін та розширення функціональності**

* **Додавання нової функціональності:**
    1.  Визначте вимоги до нової функції.
    2.  Створіть відповідні UI-елементи (макет XML, Fragment/Activity).
    3.  Створіть або модифікуйте ViewModel для керування даними та логікою нової функції.
    4.  Створіть або модифікуйте Repository для доступу до даних, необхідних для нової функції (можливо, знадобиться модифікація DAO та Entity).
    5.  Реалізуйте необхідну бізнес-логіку в ViewModel та/або Repository.
    6.  Зв'яжіть UI-елементи з LiveData у ViewModel для відображення даних та обробки дій користувача.
    7.  Напишіть юніт- та UI-тести для нової функціональності.
    8.  Задокументуйте зміни.

* **Зміна існуючої функціональності:**
    1.  Проаналізуйте існуючий код та визначте необхідні зміни.
    2.  Внесіть зміни до відповідних класів (UI, ViewModel, Repository, Model).
    3.  Переконайтеся, що зміни не порушують роботу іншого функціоналу.
    4.  Оновіть тести відповідно до внесених змін.
    5.  Задокументуйте зміни.

* **Робота з базою даних (Room):**
    * При зміні схеми бази даних (додавання/видалення стовпців, таблиць), необхідно оновити відповідні Entity-класи та збільшити версію бази даних у класі `AppDatabase`.
    * Для збереження даних користувачів при зміні схеми необхідно надавати класи міграцій (`Migration`). Для початкової розробки можна використовувати `fallbackToDestructiveMigration()`, але для production-версії це неприпустимо.
    * Для виконання нових запитів до бази даних необхідно додавати відповідні методи до DAO-інтерфейсів з використанням анотації `@Query`.
