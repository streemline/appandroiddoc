package com.example.timetracker.data.local.dao {
  interface TimeEntryDao {
    @Query("SELECT * FROM TimeEntries ORDER BY date DESC, startTime DESC")
    fun getAll(): LiveData<List<TimeEntry>>

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insert(timeEntry: TimeEntry)

    @Update
    suspend fun update(timeEntry: TimeEntry)

    @Delete
    suspend fun delete(timeEntry: TimeEntry)

    @Query("SELECT * FROM TimeEntries WHERE strftime('%Y-%m', date) = :month ORDER BY date DESC, startTime DESC")
    fun getTimeEntriesForMonth(month: String): LiveData<List<TimeEntry>>

    @Query("SELECT SUM(duration) FROM TimeEntries WHERE strftime('%Y-%m', date) = :month")
    fun getTotalDurationForMonth(month: String): LiveData<Long>
  }

  interface UserDao {
    @Query("SELECT * FROM Users LIMIT 1")
    fun getUser(): LiveData<User>

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insert(user: User)

    @Update

  }

**Додаткові деталі щодо класів:**

* **Фрагменти (InputTimeEntryFragment, StatisticsFragment, ProfileFragment):**
    * Містять UI-елементи (EditText, Button, RecyclerView, ProgressBar тощо).
    * Спостерігають за LiveData з ViewModel для відображення даних.
    * Обробляють події користувача (натискання кнопок, введення тексту) та передають їх до ViewModel.
    * Використовують адаптери (наприклад, `TimeEntryAdapter`) для відображення списків даних у `RecyclerView`.
    * Можуть використовувати UI-компоненти (`MonthCardComponent`).
    * Можуть використовувати анімаційні компоненти для покращення UX.

* **ViewModel (TimeEntryViewModel, UserViewModel):**
    * Керують даними для відповідних фрагментів.
    * Отримують дані з репозиторіїв (TimeEntryRepository, UserRepository).
    * Перетворюють та готують дані для відображення у фрагментах (використовують LiveData для сповіщення про зміни).
    * Містять логіку обробки дій користувача (наприклад, збереження нової записи).
    * Не залежать від життєвого циклу Activity/Fragment.
    * Можуть використовувати утилітарні класи (`DateUtils`).

* **Репозиторії (TimeEntryRepository, UserRepository):**
    * Виступають як єдине джерело даних для ViewModel.
    * Інкапсулюють логіку доступу до даних (локальна база даних через DAO, мережа - якщо буде в майбутньому).
    * Виконують операції з базою даних (вставка, оновлення, видалення, вибірка).
    * Викликають класи для експорту даних (`ExcelExporter`, `PdfExporter`, `CSVExporter`).
    * Можуть обробляти результати операцій (наприклад, повертати `Result` для обробки успіху/помилки).

* **DAO (TimeEntryDao, UserDao):**
    * Інтерфейси, що визначають методи для взаємодії з таблицями бази даних.
    * Анотуються Room для автоматичної генерації коду, що реалізує ці методи (SQL-запити).
    * Використовуються репозиторіями для виконання низькорівневих операцій з базою даних.
    * Можуть повертати LiveData для автоматичного оновлення даних у UI при змінах в базі даних.

* **Entity (TimeEntry, User, MonthlyReport):**
    * Класи даних, що представляють рядки у відповідних таблицях бази даних.
    * Анотуються Room для визначення їх як таблиць бази даних та їхніх стовпців (полів).
    * Містять поля, що відповідають стовпцям таблиць.

* **Утилітарні класи (DateUtils, Exporters):**
    * `DateUtils`: Містить статичні методи для форматування дат, часу, розрахунку тривалості тощо.
    * `ExcelExporter`, `PdfExporter`, `CSVExporter`: Містять логіку для експорту даних у відповідні формати. Можуть приймати список `TimeEntry` та об'єкт `User` для включення інформації у звіт.

* **UI-компоненти (AnimatedVisibilityComponent, AnimatedListComponent, FadeOutAnimationComponent, MonthCardComponent):**
    * Кастомні View або композиції View, що інкапсулюють певну UI-логіку та візуальне представлення.
    * `MonthCardComponent` відповідає за відображення зведеної інформації за місяць.
    * Анімаційні компоненти використовуються для створення плавніших та привабливіших переходів та оновлень UI.

### 2. Деталізована структура бази даних

Структура таблиць залишається такою, як описано в попередньому розділі, але додамо деякі важливі аспекти:

**1. Таблиця `Users`:**

* **`userId` (INTEGER, PRIMARY KEY, AUTOINCREMENT):** Унікальний ідентифікатор користувача. Автоматично генерується базою даних.
* **`name` (TEXT, NOT NULL):** Ім'я користувача. Обов'язкове поле.
* **`hourlyRate` (REAL, DEFAULT 0.0):** Погодинна ставка користувача. За замовчуванням 0.0.
* **`settings` (TEXT, JSON формат для зберігання додаткових налаштувань):** Може використовуватися для зберігання різних налаштувань користувача у форматі JSON (наприклад, вибрана тема, мова тощо).

**2. Таблиця `TimeEntries`:**

* **`entryId` (INTEGER, PRIMARY KEY, AUTOINCREMENT):** Унікальний ідентифікатор запису робочого часу. Автоматично генерується.
* **`userId` (INTEGER, NOT NULL, FOREIGN KEY REFERENCES Users(userId) ON DELETE CASCADE):** Ідентифікатор користувача, якому належить цей запис. Зовнішній ключ, що посилається на `userId` в таблиці `Users`. `ON DELETE CASCADE` означає, що при видаленні користувача всі його записи робочого часу також будуть видалені.
* **`date` (TEXT, NOT NULL, формат `YYYY-MM-DD`):** Дата виконання роботи. Обов'язкове поле у стандартизованому форматі для зручного сортування та фільтрації.
* **`startTime` (TEXT, NOT NULL, формат `HH:MM`):** Час початку роботи. Обов'язкове поле у 24-годинному форматі.
* **`endTime` (TEXT, NOT NULL, формат `HH:MM`):** Час закінчення роботи. Обов'язкове поле у 24-годинному форматі.
* **`duration` (INTEGER, NOT NULL, кількість хвилин):** Розрахована тривалість робочого часу в хвилинах. Зберігання тривалості окремо може спростити деякі статистичні запити.
* **`notes` (TEXT):** Додаткові нотатки або опис виконаної роботи. Необов'язкове поле.
